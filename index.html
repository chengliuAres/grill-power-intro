让 AI 写代码别再「瞎改」

一个按风险分级的多 Agent 开发工作流 —— 想透，写少；风险越高，流程越深。给 AI 一个需求，它先判断「改错了的代价有多大」，再挑一条深浅相称的流程：改个函数走最轻的路，动数据库走最重的路。

01

业务背景与问题介绍

AI 编码已经进入日常，但「给 AI 立规矩」这件事普遍踩在两端的坑上：小改动被重流程拖垮，大改动缺纪律翻车。根因不是流程多或少，而是用一套固定流程对付风险天差地别的任务。

翻车现场 ① · 过度治理

小改动被重流程拖垮

改个函数名、补个判空，一分钟的事，AI 却要你陪它走一遍 TDD、写份 spec、再来两轮 review —— 半小时就没了。大部分时间耗在「流程」而不是「问题」上。

更要命的是，流程太重，人的第一反应是绕道：不改了，或者偷偷改，规矩形同虚设。

代价：流程被架空，有纪律但太重
翻车现场 ② · 治理不足

大改动缺纪律翻车

碰到跨三个模块、还要动数据库结构的改动，AI 又变得异常勇敢：没摸过代码就开始设计，没做过压力测试就动手，最后「解决得漂漂亮亮」。

可方向一旦错了，越漂亮越返工。

代价：方向性返工，有信任但太散
深挖

一个会话从头干到尾，必然撞上三堵墙

墙 ①

上下文天花板

为改一个小功能读十个文件，原文全堆在同一个会话里。读到最后，注意力被大量无关代码稀释——该记住的约束忘了，不该改的地方改了。

信噪比随材料堆积而下降
墙 ②

角色冲突

同一个会话先「设计方案」，再「实现方案」，最后「审查方案」——天然倾向于确认自己前面的判断。不是模型不诚实，是决策层的自我背书。

既当运动员又当裁判
墙 ③

自我审查盲区

让写代码的会话审自己写的代码，满脑子是「我为什么这么写」——漏掉的边界条件，它根本想不起来去查。

审了，但等于没审
根因：拿一套固定流程，去对付风险天差地别的任务
低风险任务被过度治理，高风险任务被治理不足。AI 需要一个「知道这次该走多深」的判断，而没人告诉它。
对照

现有工具怎么解：三家各有所长，也各缺一块

工具精髓（值得拿走的）缺的那块
openspec spec 驱动：提案/规格/任务全程留痕（propose → archive），决策可追溯 全文档链一刀切——小改动也要背 spec 税负，流程深度不随风险伸缩
Superpowers 过程纪律工具箱：brainstorming / TDD / writing-plans / systematic-debugging，每类任务有成熟套路 按「任务类型」选套路，不按「风险」分深浅——轻改与重构付同等流程成本

grill-me · 问透 + openspec · 沉淀 + Superpowers · 纪律 → grill-power

取法：grill-me 的「问透」裁剪成工程节奏（先探索代码再问、批量 ≤3 问、Decision Gate 一次确认）；openspec 的「沉淀」只在 Full 档动用（落 plan + Plan Gate，高风险才背文档税负）；Superpowers 的「纪律」互认边界（验证复跑、根因未收束转 systematic-debugging）。三家都没覆盖的两块空白——按风险分级 × 多 Agent 编排——正是它自己的创新，见 02。

02

项目创新性

grill-power 的想法只有八个字：「想透，写少；风险越高，流程越深。」像机场安检：随身行李快速过，可疑箱包开箱查 —— 让流程深度跟着风险走，而不是跟着任务大小走。它不是拍脑袋设计的，一个月 45 个 commit、十余组端到端场景评测，每个机制背后都是一次真实踩出来的坑。

核心思想：两条主线咬合，而非简单叠加

很多人第一次看它会以为这是个「多 Agent 工作流」——只说对了一半。它是问题分级 × 多 Agent 编排的上下游咬合：先分诊，再排医生。

主线 ② · 排医生

多 Agent 编排

回答：如果上，该派谁去干？

四个角色（explore / reader / coder / reviewer）→ 五槽契约派活 → 双维度审查
关键限定：Lite 档全程零 subagent，只有 Standard / Full 才起多 Agent 编排。这不是省事，而是纪律——Agent 数量本身是成本（多一份上下文开销、多一层协调成本），科室齐全不等于每个感冒都要会诊。
创新点 1

按风险分级：看「改错了会怎样」，而非「改了多少」

第一个反直觉的设计：任务大小和风险并不正相关。500 行但逻辑直白的改动，风险可能远低于 30 行却改到启动流程或协议字段的改动。所以分级看四个维度——依赖范围 · 风险 · 影响面 · 可验证性；两条原则——就高不就低（存疑升档，高风险不可逆操作不得低于 Full）、升档看风险不看任务数量（防止「为了安全而安全」的过度治理）。

创新点 2

多 Agent 编排：四个角色 + 五槽契约，缺一槽不派

按角色路由，而不是按任务路由——不是「任务复杂就派三个 Agent 一起上」，而是「现在需要哪种能力就派哪个角色」，像真实项目组一样分工。角色分工还顺带打开成本杠杆：粗活用便宜快的模型，实现和审查才用强模型。

角色一句话职责典型触发类比项目组
explore广度定位：按关键词/符号定位相关文件与入口Standard/Full 探索阶段默认派调研员——先摸清地形画张地图
reader精读理解：读指定文件/区间，返回结构化摘要（≤30 行）explore 输出不足以确认实现/约束时精读员——把关键文件读透交一页摘要
coder实现：按 task 在文件白名单内实现 + task 级验证预估 >5 文件或 >300 行，或预估不确定工程师——划定范围内施工，越界即停
reviewer独立审查：需求覆盖/边界回归/入口引用/验证证据实现完成后默认派质检员——只审不写

创新点 3

双维度审查：独立上下文是底线，异模型是增强项

整套设计里最容易被糊弄、也最要紧的一环。用两个正交维度定义「有效审查」：独立上下文（reviewer 必须是独立 agent 会话——「换个没参与的人来审」，底线不能丢）+ 异模型（reviewer 模型 ≠ 主会话且 ≠ coder，且必须已验证——「再换副不同牌子的眼镜」，增强项可丢）。退化顺序：先丢异模型保独立上下文；链尽 = 主会话自审 + 显式声明，禁写「独立审查通过」。

最低要求

独立上下文

  • reviewer 是独立的 agent 会话，不是主会话自己（隔离既有结论/偏见）。
  • 算：原生 spawn / workflow agent / codemaker run -m / 同模型 subagent。
  • 只有「主会话自审」不算。
增强项

异模型

  • reviewer 模型 ≠ 主会话模型 且 ≠ coder 模型，交叉抵消单模型盲区。
  • 须「已验证」：原生回显 effective model，或 codemaker model-list 解析 model ID。
  • 碰撞（如 oracle = 主模型）时沿降级链换 codemaker run -m。

创新点 4

工程韧性：路由矩阵 + 降级链 + 上下文卫生 + 渐进加载

流程能跨工具活下来、跑久了不变形，靠四件不起眼的工程事：

换环境不哑火

路由矩阵 + 降级链

  • 不同工具创建 subagent 的方式完全不同，怎么喊人不能写死：先探测环境，再按（环境 × 角色 → 通道/模型）选通道——5 个环境分片 × 4 个角色，每格写死主选通道与模型档位，点开看完整矩阵。
  • 主选通道不可用/失败/超时，按逐档退化，退到哪一档必须显式说出来（铁律 6）。
  • 经验：通道的能力边界会反过来约束角色纪律——主选通道曾因为「派出去的 Agent 无法追问」而整体更换。
主会话不被灌爆

上下文卫生：薄回传

  • explore 只回 文件:行号+一句事实；reader 回 ≤30 行摘要；coder 回固定四段；reviewer 详报落盘、只回计数+路径。
  • 对冲纪律：coder 自报的验证结果只作参考，主会话必须自己复跑至少一条关键验证命令。
  • 详报落盘带唯一 run-id、不覆盖——三个月后还能查「当时到底审了什么」。
skill 自己也要轻

渐进式加载：用到哪页翻哪页

  • 低频内容下沉到 references（Full 流程、问题设计、Plan Gate、各环境路由分片）。
  • 主文件只留分级判定、铁律、流程骨架和加载索引——主文件减重 24%，顺跑路径上下文占用明显下降。
底线钉死

两个 Gate + 11 条铁律

  • Decision Gate 定「做什么」、Plan Gate 审「怎么做」——需求错了计划再完美也没用。
  • 最不能破的底线抽成 ，全流程只引用编号、不重述，防止规则膨胀。
  • 铁律 1 治「凭想象设计」、铁律 6 治「自己审自己还说通过」、铁律 9 治「把同事没提交的改动卷进来」。
创新点 5

Loop 设计：返工不烦你，拍板才找你

流程里跑着六层有界循环（Bounded Loop）——Plan Gate 退回、审查打回自动重修、复审验证回归、coder 追问延续，技术性返工全自动，你不用盯着它改到第几遍。但每一层都钉了硬上限，到上限就停下交人。因为无人流程最大的风险从来不是不干活，而是停不下来——无限重试等于烧 token 的死循环。

循环层级硬上限到上限怎么办
Plan Gate 退回仅一次修正后自审放行、不再派 reviewer；高风险任务暂停交用户
复审（Full）只复审一次仍不通过或范围扩大时，暂停交用户
复审（Standard）最多一次仍不通过时，暂停汇报
Grill 回归Standard 1 轮 / Full 2 轮转待确认清单
模式升档同一任务最多一次再次范围扩张，暂停交用户重新定范围
coder 追问≤2 轮第 3 次必须开新会话、只带结论

分界线很清楚：能从代码自证的事它自己跑（审查发现问题自动重修、修完自动复审），需要拍板的事必须停下来问你——业务语义不明、要删能力、要动 DB schema / 协议 / 迁移回滚时，规则明确写着「不得以推荐值代答」，高风险任务退回后禁止自审放行。人的介入不是被消灭，是被压到了不可逆决策点上：返工不烦你，拍板才找你。

诚实的边界：这套循环活在单次会话内——跨会话的长时任务仍需人重新发起，任务级自动续跑的调度层尚未建设。但这六层「有上限 + 越界交人」的纪律，恰恰是将来做长时自闭环的前置安全底座：没有它，无人值守的第一步就会撞上停不下来的死循环。
03

价值贡献

它想解决的本质是一个「治理成本」问题。对使用者来说答案很直接——提效：你只管说一句话需求，分级、派活、挑模型、审查兜底全自动。下面四笔账，笔笔有出处。

第 1 笔 · 省认知

不需要懂多 Agent 怎么干活

  • 一句话入口：/grill-power 优化一下首页加载，剩下的事它自己安排——你看到的是一次结构化汇报，背后是整条流水线。
  • 派几个 Agent、派谁、配什么模型，全自动；粗活用便宜快的模型、实现和审查才用强模型，你不用替它挑。
  • 触及 DB schema / 协议 / 启动流程 / 迁移回滚 / 删除能力时自动加载兜底，不唤起也兜住高风险改动。
  • 多端通用：iOS / Android / C++ / Flutter / RN / Web / Figma 还原。
第 2 笔 · 省 token

主会话上下文不爆炸

  • 渐进式加载：低频规则「用到哪页翻哪页」，主文件实测减重 24%，顺跑路径占用明显下降。
  • 薄回传：explore 只回 文件:行号+一句事实；reader 回 ≤30 行摘要；reviewer 详报落盘、只回计数+路径——subagent 拿一手材料，交回来的只有结论和指针。
  • 相比 spec 类重流程（openspec 的 propose → plan → archive 全文档链 + Superpowers 流程），实测 token 消耗降低 30%+（组内真实交付统计）。
第 3 笔 · 省时间

流程深度匹配风险，不一刀切

  • 小事走 Lite：几分钟交付，零 subagent、不落 plan——一分钟的改动不再被拉成半小时。
  • 大事走 Full：可证明独立的 task 才并行——并行是单会话给不了的（一个会话只有一条时间线）。
  • 流程不再是所有改动都要交的「时间税」。
第 4 笔 · 实战检验

真实交付：质量可靠，返工率为 0

  • 组内深度使用、反馈驱动迭代：累计 45 次版本升级，沉淀 10+ 组端到端场景评测。
  • 邮箱大师客户端全场景适配中，Q3 15+ 需求采用本工作流交付：零延期、返工率为 0。
  • 读信核心协议一次改动 27 个文件：一次编译通过、零回归、交付 bug 为 0，工期由 4 人天压到 2 人天（提效 50%）。
  • 底气来自机制：小改动零 subagent 几分钟交付；高风险改动（协议 / schema / 迁移 / 删能力）强制完整流程、不得降级。

第三方视角：AI 洞察报告怎么说

这份报告不是自评——它由公司 CodeMaker 平台基于真实使用行为自动生成，下图为原始截图、数值未作处理。它从会话行为里自主识别出的三个特征，恰好对应本文的三个机制。

报告识别出的三条特征与本文机制一一对应：子代理分工并行 → 多 Agent 编排（创新点 2）、多模型交叉评审 → 双维度审查（创新点 3）、交付稳定性 → 实战质量数据（第 4 笔）。

就算不用它，这六条也值得带走

工具无关的设计原则，在任何 AI 编码工具里都能自己搭一套：

01给 AI 的流程按风险分档，别一套流程走天下。
02该派几个 Agent 由风险决定，不是越多越好——小事自己干更快。
03派活前把「职责/输入/输出/禁止/停止条件」五槽契约组装齐，缺一槽不派。
04自审 ≠ 独立审查，重要改动找个「没参与」的模型挑错，并如实说明是自审还是他审。
05subagent 的自报结果只作参考，关键验证自己复跑一遍。
06低频规则按需加载，别每次对话都塞满上下文。
诚实的边界：它不是银弹——根因未收束的系统性 bug 该走系统排查流程，需要 spec 沉淀的项目该走 spec 流程；上述实战数据来自组内真实交付的统计观察，非严格双盲 A/B 实验。

4.1 三档如何划分

按 依赖 · 风险 · 影响面 · 可验证性 四维判定，存疑时就高不就低；分级看「改错了会怎样」而非「改了多少文件」，任务数量不触发升档（铁律 8）；高风险不可逆操作（DB schema / 协议兼容 / 删除能力 / 迁移回滚）不得低于 Full。需求涉及新增公开可复用能力（协议方法 / 公开 API / 工具类 / 中间层）时先做两步筛查：Q2 已有入口（是否已有权威入口或方法组合可覆盖）+ 使用方（能否说明首个调用方），命中则追加「▶ 需求存疑」行交用户裁定。

模式 进入条件 流程 落盘 / 审查
Lite 单文件/单函数 · 改法明确 · 低风险 · 无业务语义歧义 成功标准 → 核对事实 → 改动 → 验证 → 自审 不落 plan；主会话自审
Standard 1~2 模块 · 无共享状态/双向依赖 · 有方案歧义 · 无高风险不可逆 探索 → grill → Decision Gate → 实现 → 独立审查 默认不落 plan；审查一次
Full 跨2+模块+共享状态 / 跨3+ 或 DB schema·协议·删除能力·迁移/回滚 完整探索 → grill → 方案确认 → 拍板 → plan/Plan Gate → 分组执行（coder 串/并实现）→ 统一 review → 复审 落一个 plan；统一审查 + 复审

就高不就低；高风险不可逆操作不得低于 Full。「机械同构替换」是唯一的 Full→Standard 降级例外，须逐条核对四项条件。

4.2 四个 Agent 设计

角色靠创建、不靠预置类型。派发前按「组装骨架」五槽（职责/输入/输出/禁止/停止条件）组装契约 prompt，任一缺失不派发。Lite 全程零 subagent。

职责

矩阵主选 → codemaker run -m → 原生 subagent 不 pin → 主会话自审 + 显式声明。

同一个审查任务（需求要求新建一个实现文件和一份测试，实际两个文件都不存在）：

控制组：无角色契约约束实验组：按 reviewer 契约派发

产物一份 Findings + 两个它自己写的文件一份纯 Findings 报告

差别不在「有没有发现问题」——两组都发现了，差在发现之后干了什么。控制组把「审查者」和「实现者」混成一个人，diff 里再也分不清哪些是被审的代码、哪些是审查者自己补的，这次审查等于没发生。由此把「只审不写」写成硬边界：reviewer 对代码和 Git 只读，唯一允许写的是审查报告文件。

4.6 铁律锚点

全流程生效，各阶段只引用编号、不重述。

01先有代码证据，再问决策；不得没探索就设计。
02并发/状态机/多入口先答 Q1/Q2/Q3Q1 合并路径消并发？ Q2 是否有权威入口改道？ Q3 删除历史能力会丢什么？
03业务语义、删除能力、外部依赖无法确认必须询问；技术细节按现有模式决定。
04每个决策只确认一次；低风险默认值直接采用并记录。
05只改需求涉及内容；不自动 commit / push / merge / 删除分支。
06自审不得写成「独立审查通过」；任一维度降级都显式声明原因。
07「继续/嗯」只在按推荐方案执行且无未决项时才算确认；跳过 Grill 不跳过 Decision Gate。
08升档只看依赖、风险、影响面、可验证性；任务数量不触发升档。
09区分本次改动与外部未提交改动；不 stash / reset / 覆盖。
10references 按触发点读取，禁止预加载；冲突以本文为准。
11Subagent 按角色路由；Lite 零 subagent。
